# 指标预聚合与时序存储（实现需求）

> 来源：业主 2026-09-24 沟通共识。对照原始需求九段（`docs` 外原文以业主粘贴为准）。  
> 事实 = 原始需求已写明；决策 = 本次沟通拍板；待确认 = 仍须对方 IoT 核对。

## 1. 目标

统计、趋势、总览类指标：**写入时落入计算桶**，查询只读桶；补传按业务时间 `recognizedAt`/`observedAt` 修正对应历史桶。不在打开页面时对明细做全量 `GROUP BY`。

规模预留：基线约 30 棚 / 110 路、1～5 分钟上报；设计与选型按 **×10** 头寸（明细上亿行量级、图可达数十 TB）验证路径，不必先换 TDengine。

## 2. 桶可计算 vs 业务服务（摘自原始需求）

### 2.1 适合预聚合桶

| 需求段 | 能力 | 桶粒度（最低） |
|---|---|---|
| （二） | 总览计数/均值/今日识别与抓拍、单棚增量、环境 24h | 小时 + 日 |
| （四） | 时/日/周/月曲线、菌盖均值、成熟率、棚间对比 | 小时 + 日（周/月由日桶再卷） |
| （五） | 高发时段/棚统计 | 小时或日 |
| （六） | 当日可采成熟数量 | 日（可再按棚） |
| （七） | 报表中的汇总数字 | 读日/月桶 |
| （八） | 在线率类统计 | 小时或日 |

**实现：** PostgreSQL 明细表保留溯源与幂等；`metric_buckets_hour` / `metric_buckets_day`（或扩展现有 `daily_aggregates`）在 ingest **成功写入且非重复** 后做增量 upsert；键含 `shedCode`[+`cameraCode`]、桶起止时间、指标名。补传同一幂等键不双计；晚到数据更新历史桶，不按到达日入桶。

### 2.2 不适合纯桶（业务服务，可读桶）

| 需求段 | 能力 | 实现 |
|---|---|---|
| （三） | 阈值、三级告警、闭环、推送 | 规则引擎 + 告警/处置表；阈值比较可读最新桶或窗口 |
| （四） | 批次出菇/快速生长/成熟期、全周期叙事 | 批次实体 + 事件；曲线仍读桶 |
| （五） | 病害档案检索、与环境联动说明 | 病害记录表 + 按时间窗查环境桶/明细 |
| （六） | 采摘任务清单、2～3 天产量预测、排班辅助 | 任务表 + 预测服务（输入为近窗桶） |
| （七） | Excel 筛选预览导出打印 | 报表服务读桶/业务表生成文件 |
| （九） | 棚级权限、审计 | 查询层按角色过滤；审计独立表 |

## 3. 时序存储决策

| 项 | 决策 |
|---|---|
| 指标库 | 继续 PostgreSQL；按 ×10 预留启用 **TimescaleDB**（PG 扩展）做明细 hypertable / 压缩 / 保留策略 |
| 不先上 | TDengine（另栈运维与双写成本；当前路径 PG+桶足够） |
| 查询 | 趋势/总览/报表汇总 **只读桶**；明细仅用于溯源、补传纠错、单帧凭证 |
| 图 | 对象存储（MinIO/云 OSS）；库只存路径。热 30～90 天，更早冷/归档。数 T 成本靠生命周期，不进 PG |

## 4. 相对现行实现的差距

现行：`metric_buckets_hour` / `metric_buckets_day`。识别 ingest 按业务时间增量 upsert 小时桶与日桶，不写 `daily_aggregates`（`010_drop_daily_aggregates.sql` 删表）。趋势、总览、大屏、病害高发读桶。小时 cron 重建昨+今、采摘修正蘑菇数后，仍 `refreshDay` 重扫该日识别明细并回写识别指标桶；环境桶保留。

下面是相对「只有 `daily_aggregates`、趋势读日表」时写下的改动。ingest 增量、小时桶、环境入桶、Timescale 可选 NOTICE 已落地。采摘修正与小时回写仍整日重扫识别明细，因为原地改数不能再做一次增量加计。

须改为：

1. **增量 upsert**（非整日重扫明细），含补传纠历史桶  
2. **小时桶**（支撑（二）24h、（四）按小时）  
3. 环境读数同样入桶  
4. Timescale：compose/文档与迁移路径（可先 PG 表结构兼容，再开扩展）  
5. 烟测：补传旧时间戳成功修正对应桶；幂等不双计（已有部分）
